## 1. 작업 개요

- 이번 작업 단위에서 만들기로 한 것: Apify Actor로 세 기관의 실제 공지 목록을 수집하고, 결과를 공통 `NoticeInput[]` 계약으로 검증한다.
- 실제로 완료한 범위: Apify MCP 연결과 Actor 입력·비용 모델을 확인하고 세 출처의 실제 목록을 수집했다. 각 출처에서 제목·게시일·절대 원문 URL·수집 시각을 검증해 유효 행 10건씩 추출했다.
- 범위에서 제외하거나 다음으로 넘긴 것: JSON fixture와 자동 검증 테스트 구현은 아직 남아 있으며, W11의 Supabase upsert 및 `crawl_runs` 기록은 워크스페이스 지출 한도 때문에 실행하지 못했다.

## 3. 구현 판단

- 선택한 구조 또는 접근: 학교 HTML 요청은 모두 Apify 공식 `apify/rag-web-browser` Actor에서 수행했다. 중앙도서관·국제언어교육센터는 기본 HTTP 추출, 산학협력단은 JavaScript 렌더링이 필요한 것을 확인해 브라우저 추출로 독립 재실행했다.
- 대안과 선택 이유: 앱 코드의 직접 `fetch`·`cheerio` 파싱이나 다른 크롤러는 PRD/AGENTS의 Apify 전용 경계를 위반하므로 사용하지 않았다.
- PRD 또는 기존 구현과의 관계: 결과는 `sourceId`, `title`, KST 기준 `publishedAt`, 절대 `originalUrl`, `scrapedAt`으로 정규화했다. 최근 7일 조회는 W12의 날짜 유틸리티가 담당하므로 오래된 유효 공지도 삭제하지 않았다.

## 4. 문제 및 막힌 지점

- 증상: Supabase `execute_sql`로 기존 행 조회·upsert 전 검증을 시도했을 때 워크스페이스 소유자가 설정한 지출 한도 초과로 요청이 거부됐다.
- 재현 방법: Supabase 프로젝트 `gcckxsabdzqkewzfbzmj`에 읽기 SQL을 실행한다.
- 원인: Codex 워크스페이스의 Supabase 작업 지출 한도이며, SQL 문법·RLS·Apify 결과 오류가 아니다.
- 영향을 받은 범위: W11의 `notices` upsert, `crawl_runs` 성공/실패 기록, 저장 표본 재검증. 현재 DB의 기존 데이터는 유지된다.

## 5. 해결 방법

- 시도한 방법: Apify 실행 전 연결 확인, Actor 입력 스키마 확인, 세 출처 독립 실행, 산학협력단의 브라우저 렌더링 재시도, Supabase 프로젝트·테이블 실제 상태 읽기를 수행했다.
- 최종 해결책: 지출 한도를 올린 뒤 W10 fixture 테스트를 마무리하고, 운영자가 다시 `공지 갱신해줘`를 요청하면 이번 수집 결과를 새로 실행·검증해 W11에서 upsert한다.
- 같은 문제가 재발할 때 확인할 항목: Supabase 앱의 워크스페이스 지출 한도, 프로젝트 `gcckxsabdzqkewzfbzmj` 접근, `notices`와 `crawl_runs`의 서비스 역할 쓰기 권한.

## 7. 미해결 사항 및 위험

- 남은 문제: 실제 Apify 결과 JSON fixture·검증 테스트가 아직 없고, 데이터베이스 반영·운영로그 기록을 하지 못했다.
- 임시 처리 또는 mock: 없음. Apify 결과를 로컬 mock이나 직접 크롤러로 대체하지 않았다.
- 외부 키·계정·콘텐츠 의존성: Apify OAuth는 정상이다. Supabase 작업 지출 한도를 소유자가 올려야 쓰기와 표본 조회가 가능하다.
- 다음 작업에 영향을 줄 위험: DB가 비어 있어 현재 공지 UI는 실제 저장 공지를 보이지 않는다. 수집 결과를 장시간 재사용하지 말고, 한도가 해소된 뒤 새로 수집해 최신 상태로 반영해야 한다.
