## 3. 구현 판단

- 선택한 구조 또는 접근: `src/lib/supabase/public.ts`는 `NEXT_PUBLIC_SUPABASE_URL`과 publishable key만 받아 `null` 또는 읽기 클라이언트를 반환하고, `server.ts`는 `server-only` 경계 안에서만 secret key로 쓰기 클라이언트를 만든다.
- 대안과 선택 이유: 사용자 사진·도감은 계속 IndexedDB 전용으로 유지하고 Supabase에는 `notices`, `crawl_runs`만 둔다. Auth/profile 테이블을 만들지 않았다.
- PRD 또는 기존 구현과의 관계: W08의 플러그인 증거만 외부 연결 문제로 보류됐지만, 사용자가 그 부분을 보류하도록 지시했고 W09의 독립 코드·원격 Supabase 검증은 P0 흐름을 약화시키지 않아 우선 진행했다.

## 4. 문제 및 막힌 지점

- 증상: 이전 W09 구현 단계에서는 Supabase 플러그인 미인증으로 후속 마이그레이션의 원격 적용과 Advisor 검증이 남아 있었다.
- 재현 방법: `docs/dev-logs/2026-08-25_1610_W09_in-progress.md`의 플러그인 상태를 확인한다.
- 원인: 세션별 플러그인 인증 상태가 달랐다.
- 영향을 받은 범위: `crawl_runs` 실패 행 비공개, anon 권한, Security Advisor의 실제 확인.

이번 세션에서 Supabase 플러그인이 정상 연결돼 같은 프로젝트(`gcckxsabdzqkewzfbzmj`)에 마이그레이션을 적용하고 검증했다. 구현을 중단시킨 문제는 없었다.

## 5. 해결 방법

- 시도한 방법: 현재 Supabase 프로젝트를 플러그인으로 조회하고, 후속 마이그레이션을 적용한 뒤 postgres 역할 전환 검증과 Advisor를 실행했다.
- 최종 해결책: 새 정책 `public read successful crawl runs`으로 기존 공개 정책을 교체했다. anon 역할의 임시 성공·실패 실행 행 조회에서 성공 행만 반환됐고 트랜잭션은 롤백했다.
- 같은 문제가 재발할 때 확인할 항목: `crawl_runs`의 anon SELECT policy가 `status = 'success'`인지, anon INSERT 권한이 false/거부인지, Security Advisor가 빈 목록인지 확인한다.
