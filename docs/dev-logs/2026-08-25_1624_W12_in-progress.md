## 1. 작업 개요

- 이번 작업 단위에서 만들기로 한 것: 장소별로 Supabase의 최근 7일 공지를 읽고, 제목·게시일·새 탭 원문 링크·마지막 성공 갱신 시각·상태 화면을 보여주는 UI를 만든다.
- 실제로 완료한 범위: 공개 Supabase 읽기 클라이언트로 출처와 KST 7일 경계를 적용하는 Client Component, KST 표시 형식, 로딩·빈 결과·조회 오류 재시도·오프라인 안내 UI를 구현했다.
- 범위에서 제외하거나 다음으로 넘긴 것: 실제 Octoparse 결과에서 생성된 공지 행과 원문 링크의 브라우저 검증은 W10/W11이 완료된 뒤 수행한다.

## 3. 구현 판단

- 선택한 구조 또는 접근: 정적 페이지는 장소 맥락만 해결하고, `PlaceNoticeList` Client Component가 공개 키로 `notices`와 성공한 `crawl_runs`를 병렬 조회한다.
- 대안과 선택 이유: 학교 사이트 또는 Next.js 서버에서 직접 공지를 읽지 않았다. 이는 Octoparse 전용 HTML 추출과 브라우저 공개 읽기 전용이라는 PRD·시스템 구조를 유지한다.
- PRD 또는 기존 구현과의 관계: `source_id` 동등 조건과 `published_at >= 최근 7일 KST 경계`를 모두 쿼리에 적용해 장소 혼입과 오래된 공지 노출을 방지한다. `crawl_runs.status = success`만 조회한다.

## 4. 문제 및 막힌 지점

- 증상: 최초 로컬 브라우저 확인에서 공지 조회 오류 상태가 표시됐다.
- 재현 방법: `/places/library/notices`를 로컬 개발 서버에서 열었다.
- 원인: 기존 `.env.local`에는 카카오·Octoparse 값만 있었고 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`가 없었다.
- 영향을 받은 범위: 실제 공개 Supabase 읽기와 W12의 빈 결과 검증.

## 5. 해결 방법

- 시도한 방법: 값 자체를 출력하지 않고 환경파일에 존재하는 변수명만 확인하고, Supabase 플러그인으로 대상 프로젝트의 URL과 활성 publishable key 존재를 확인했다.
- 최종 해결책: 기존 `.env.local`을 변경하지 않고 Git 제외 규칙에 맞는 `.env.development.local`에 공개 읽기 설정을 분리했다. 개발 서버 재시작 뒤 실제 Supabase 조회가 성공해 빈 상태가 표시됐다.
- 같은 문제가 재발할 때 확인할 항목: 로컬은 `.env.development.local`, 프로덕션은 Vercel의 `NEXT_PUBLIC_SUPABASE_URL`과 `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` 설정을 확인한다. secret key는 이 UI에 사용하지 않는다.

## 7. 미해결 사항 및 위험

- 남은 문제: 세 출처의 실제 공지 행, 원문 링크, 마지막 성공 갱신 시각이 없다.
- 임시 처리 또는 mock: 없음. 빈 테이블을 실제로 조회했으며 가짜 공지를 저장하지 않았다.
- 외부 키·계정·콘텐츠 의존성: W10의 Octoparse 사용자 정의 작업 세 개와 W11의 수동 반영이 필요하다. Vercel 공개 Supabase 환경변수는 W14에서 추가·검증해야 한다.
- 다음 작업에 영향을 줄 위험: 실제 출처 데이터가 생길 때까지 행 정렬·원문 링크·최신 성공 시각의 종단 간 증거를 제출할 수 없다.
