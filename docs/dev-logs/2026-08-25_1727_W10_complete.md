## 3. 구현 판단

- 선택한 구조 또는 접근: source ID를 함수 입력으로 고정하고, 각 출처의 허용 origin에서만 원문 URL을 받아 상대 링크를 HTTPS 절대 URL로 바꾼다. 날짜는 `YYYY-MM-DD`, `YYYY.MM.DD`, `YY.MM.DD`만 허용해 KST 자정 ISO 문자열로 정규화한다.
- 대안과 선택 이유: 앱 코드에서 학교 HTML이나 Markdown을 파싱하지 않았다. Apify Actor가 HTML 추출을 담당하고 이 모듈은 이미 추출된 행의 값 검증만 담당한다.
- PRD 또는 기존 구현과의 관계: 오래된 유효 공지는 삭제하지 않고 저장하며, 화면의 최근 7일 필터는 기존 `date-kst.ts`가 적용한다.

## 4. 문제 및 막힌 지점

- 증상: 초기 수동 갱신 시 Codex Supabase SQL 호출이 워크스페이스 지출 한도로 차단됐다.
- 재현 방법: Codex Supabase `execute_sql` 호출.
- 원인: 워크스페이스 승인 한도이며 Apify 결과·DB 스키마 결함은 아니었다.
- 영향을 받은 범위: 운영자가 SQL Editor로 반영해 우회하지 않고 정상 권한 경로로 해결했으며, 실제 `notices` 30행·`crawl_runs` 3행을 확인했다.

## 5. 해결 방법

- 시도한 방법: 세 Apify Actor 실행 결과를 조사하고, 산학협력단의 `YY.MM.DD` 날짜와 상대 URL을 fixture로 재현했다.
- 최종 해결책: 타입 안전한 검증 모듈과 fixture 테스트를 추가했다. SQL Editor 수동 반영 스크립트는 같은 Apify 실행에 대해 중복 실행 로그를 만들지 않는다.
- 같은 문제가 재발할 때 확인할 항목: source origin 검사, 날짜 정규화 결과, fixture 테스트, Apify dataset의 실제 필드명.
