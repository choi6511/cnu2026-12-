## 3. 구현 판단

- 선택한 구조 또는 접근: Vercel MCP 플러그인이 이 세션에서 인증되지 않은 상태(`plugin:vercel:vercel`은 OAuth 필요, 세션이 비대화형이라 인증 불가)이므로, 대신 브라우저 도구로 프로덕션 URL에 직접 `fetch(..., {cache: "no-store"})`를 실행해 Vercel 엣지 캐시를 우회하지 않고도 실제 응답 헤더와 HTML을 확인했다.
- 대안과 선택 이유: Vercel CLI 설치·로그인도 시도했으나 CLI 미설치 + 프로젝트 토큰 없음으로 비대화형 인증이 불가능해 포기했다. GitHub Actions 워크플로도 존재하지 않아 그 경로도 없었다.
- PRD 또는 기존 구현과의 관계: `AGENTS.md` 0장은 "Vercel 플러그인으로 실제 배포 상태를 확인"하도록 요구하는데, 플러그인 인증 자체가 막혀 이 요구를 이번 세션에서 완전히 충족하지 못했다. 대신 가능한 최대한의 독립 진단을 수행했다(6장 검증 결과).

## 4. 문제 및 막힌 지점

- 증상 1: `npm ci`가 `EPERM`/`ENOTEMPTY`로 반복 실패했다.
- 재현 방법: OneDrive로 동기화되는 프로젝트 폴더에서 `node_modules`를 갱신할 때 발생.
- 원인: (a) 이전 세션이 남긴 `next dev` 프로세스(PID 4024/11256/16784)가 `node_modules/@next/swc-win32-x64-msvc`를 잠그고 있었고, (b) OneDrive 동기화가 삭제·재생성 중인 파일을 잠가 `rm -rf node_modules`가 여러 번 부분 실패했다.
- 영향을 받은 범위: 로컬 `node_modules`뿐이며, 소스 코드나 Git 이력에는 영향이 없었다.
- 증상 2 (핵심 배포 문제): 프로덕션 URL이 `93490f87d5b5c022cd169c11cf775c90f48841d6`보다 오래된 커밋을 서빙한다.
- 재현 방법: `fetch("https://cnu2026-12-five.vercel.app/", {cache:"no-store"})`로 홈 HTML을 받으면 `hero-mascot` 안에 `pose-running` 자산이 들어 있고 `mascot-front`는 없다. `/collection`에도 `pose-together`가 없다.
- 원인(진단): 응답 헤더가 `x-vercel-cache: HIT`, `age: 8101`(초)이었고 응답 `date`는 `2026-08-25 20:56:43 KST`였다. 역산하면 이 정적 페이지는 약 `2026-08-25 18:41 KST`에 생성된 것이다. 커밋 시각을 대조하면:
  - `2c821d9`(cinematic 리디자인, 홈에서 `pose-running`을 직접 사용) = `18:37:42 KST`
  - `f50d46d`/`a985a96`/`4ee4b8c`/`93490f8`(공식 마스코트로 교체, `mascot-front` 사용) = `18:4x`–`19:17:08 KST`
  - 즉 마지막으로 실제 서빙되고 있는 정적 빌드는 `2c821d9` 직후 시점의 배포이며, 그 이후 GitHub `main`에 추가된 최소 4개 커밋(마스코트 수정 3건 + 오늘 세션의 문서 커밋)이 프로덕션에 전혀 반영되지 않았다.
- 영향을 받은 범위: 프로덕션 URL 전체(홈, `/collection`). GitHub `main`과 배포된 정적 자산 사이의 동기화가 최소 약 2시간 이상 끊겨 있다.

- 같은 문제가 재발할 때 확인할 항목: Vercel 대시보드 → 해당 프로젝트 → Settings → Git에서 (a) Connected Git Repository가 `choi6511/cnu2026-12-`인지, (b) Production Branch가 `main`인지, (c) 최근 Deployments 탭에서 `main` 브랜치의 최신 커밋(`b166f35` 이상)에 대한 배포가 실제로 생성·Promote 되었는지 확인한다. 자동 배포가 안 되면 "Redeploy" 또는 새 커밋 푸시로 강제 트리거한다.

## 7. 미해결 사항 및 위험

- 남은 문제: 프로덕션 URL이 여전히 구버전 빌드(약 `2c821d9` 시점)를 서빙 중이다. GitHub `main`은 정확하지만 Vercel 프로덕션 배포가 그 뒤로 갱신되지 않았다.
- 임시 처리 또는 mock: 없음. 코드나 테스트에 임시 우회를 넣지 않았다.
- 외부 키·계정·콘텐츠 의존성: Vercel 프로젝트가 다른 팀원 소유이며(이전 W16 일지에 기록됨), 이 세션의 Vercel MCP 플러그인은 OAuth 인증이 필요한데 비대화형 세션에서는 인증을 완료할 수 없다. **사람이 클로드 코드의 대화형 세션에서 `/mcp` 또는 `claude mcp`로 Vercel 플러그인을 인증하거나, Vercel 대시보드에 직접 로그인해 아래 조치를 취해야 한다.**
- 다음 작업에 영향을 줄 위험: 이 상태로 W15(최종 회귀·발표 준비)에 진입하면 "배포 버전과 테스트한 버전이 동일하다"는 완료 조건을 충족할 수 없다. 반드시 프로덕션 재배포 확인 후 W15를 진행해야 한다.

### 사용자가 지금 해야 할 일 (Vercel 대시보드 또는 인증된 세션에서)

1. Vercel 대시보드 → `cnu2026-12-five` 프로젝트 → **Settings → Git**에서 연결된 저장소가 `choi6511/cnu2026-12-`, Production Branch가 `main`인지 확인한다.
2. **Deployments** 탭에서 최신 커밋(`b166f35`, 그 이전 `93490f8`)에 대한 배포가 생성되어 있는지 확인한다. 없다면 GitHub 웹훅 연결이 끊어졌거나 배포 권한 문제일 수 있다.
3. 배포가 생성되어 있는데 Production으로 Promote되지 않았다면 최신 배포를 Promote to Production 한다.
4. 배포 자체가 없다면 **Redeploy**(기존 배포 재시도) 또는 `main`에 새 커밋을 푸시해 강제로 새 빌드를 트리거한다.
