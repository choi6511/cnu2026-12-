## 3. 구현 판단

- 선택한 구조 또는 접근: PRD에 정의된 두 테이블만 `public`에 생성하고 `source_id`는 세 장소 문자열로 제한했다. 두 테이블은 동일 출처 식별자를 사용하지만 물리 FK는 만들지 않았다.
- 대안과 선택 이유: 별도 `sources` 테이블이나 `crawl_run_id` FK를 추가할 수 있으나, 세 장소가 정적 로컬 데이터이고 공지와 특정 실행의 연결이 PRD에 없으므로 다음 작업 범위를 선행하지 않았다.
- PRD 또는 기존 구현과의 관계: 사용자·인증사진·캐릭터 획득 이력은 서버에 저장하지 않고 IndexedDB에 둔다는 PRD 제외 범위를 지켰다. 성공 실행은 `error_message is null`, 실패 실행은 비어 있지 않은 오류 메시지를 갖도록 제약했다.
- 작업 순서 판단: `docs/DEVELOPMENT_PRIORITY.md`상 W00부터 시작해야 하지만 사용자가 W09의 DB 하위 범위를 명시적으로 요청했다. 선행 앱 코드에 의존하지 않는 DDL·ERD만 수행하고 W09 전체를 완료로 판정하지 않았다.

## 4. 문제 및 막힌 지점

- 증상: 저장소에 애플리케이션 코드, Git 저장소, Supabase 연결 환경변수와 기존 개발일지가 없었다.
- 재현 방법: 루트 파일 목록, `git status`, `package.json`, `.env` 변수명 및 `docs/dev-logs/` 확인
- 원인: 현재 폴더에는 PRD/SPEC/발표 자료만 있고 W00 앱 골격이 아직 생성되지 않았다.
- 영향을 받은 범위: W09의 클라이언트 코드, 날짜 유틸리티, 타입/린트/빌드 및 브라우저 기반 공개 키 검증을 수행할 수 없었다.

원격 DB 생성 자체는 Supabase 플러그인 연결 후 막힘 없이 진행됐다. 적용 전 `public` 테이블과 마이그레이션이 모두 비어 있음을 확인했다.

## 5. 해결 방법

- 시도한 방법: 로컬 CLI/DB 연결 여부를 확인하고 Supabase 연동 플러그인을 설치·연결했다.
- 최종 해결책: 재현 가능한 SQL 마이그레이션을 먼저 작성한 뒤 활성 프로젝트에 적용하고 PostgreSQL 카탈로그와 역할 전환 테스트로 결과를 재검증했다.
- 같은 문제가 재발할 때 확인할 항목: Supabase 프로젝트가 둘 이상이면 대상 프로젝트를 사용자에게 확인하고, 적용 전 `public` 테이블과 마이그레이션 충돌을 먼저 조회한다. 비밀 키 값은 출력하거나 저장소 파일에 기록하지 않는다.

- 남은 문제: W09 완료 조건 중 브라우저/서버 클라이언트 분리와 KST 7일 경계 테스트가 남아 있다.
- 임시 처리 또는 mock: 없음. 검증용 INSERT는 모두 트랜잭션에서 롤백했다.
- 외부 키·계정·콘텐츠 의존성: Supabase 프로젝트 연결은 완료됐지만 앱에서 사용할 publishable/secret 환경변수 설정은 아직 하지 않았다.
- 다음 작업에 영향을 줄 위험: W00–W08 선행 작업이 실제 코드로 존재하지 않는다. 현재 폴더에서 W09 앱 통합을 먼저 확장하면 우선순위 규칙과 의존성이 깨진다.
- 확인한 경계 조건: 허용되지 않은 `source_id`, 음수 `item_count`, 성공 실행의 오류 메시지, 실패 실행의 빈 오류 메시지, 종료 시각이 시작 시각보다 빠른 실행을 DB 제약이 거부한다.
