## 3. 구현 판단

- 선택한 구조 또는 접근: `public/sw.js`를 의존성 없는 최소 Service Worker로 두고, 정적 소개·도감·이미지와 오프라인 안내만 캐시한다.
- 대안과 선택 이유: 지도 SDK·타일과 Supabase Data API 응답을 캐시하면 오래된 지도·공지 데이터를 최신처럼 보이게 할 수 있으므로 같은 출처가 아닌 요청을 명시적으로 무시했다.
- PRD 또는 기존 구현과의 관계: Service Worker는 네트워크 우선·`skipWaiting`·`clients.claim`·구 캐시 삭제로 새 배포가 오래된 캐시에 가려지는 위험을 줄인다. 인증사진은 기존처럼 IndexedDB에 남으며 서버 전송은 추가하지 않는다.

## 4. 문제 및 막힌 지점

- 증상: 첫 타입 검사와 빌드에서 manifest icon의 `purpose: "any maskable"`이 Next의 `MetadataRoute.Manifest` 타입에 맞지 않았다.
- 재현 방법: `npm run typecheck` 또는 `npm run build` 실행.
- 원인: Next 16이 노출하는 타입은 단일 아이콘 purpose 값만 허용한다.
- 영향을 받은 범위: 타입 검사와 프로덕션 빌드.

## 5. 해결 방법

- 시도한 방법: manifest 타입 오류 위치를 확인했다.
- 최종 해결책: 두 아이콘의 purpose를 타입과 의미에 맞는 `maskable` 단일 값으로 변경했다.
- 같은 문제가 재발할 때 확인할 항목: manifest의 `display`, `start_url`, 각 icon `sizes`와 `purpose`를 `MetadataRoute.Manifest` 타입 검사로 확인한다.

## 7. 미해결 사항 및 위험

- 남은 문제: HTTPS 프로덕션에서 Service Worker 등록, Chrome 설치 인식, 소개·도감 오프라인 및 지도·공지 안내를 실제로 확인해야 한다.
- 임시 처리 또는 mock: 없음. 브라우저 Service Worker API 관찰 제약 때문에 실제 등록 성공을 추정하지 않는다.
- 외부 키·계정·콘텐츠 의존성: W14의 Vercel 배포와 실제 Chrome/모바일 기기 확인이 필요하다. W10/W11 Octoparse 작업은 여전히 별도 차단 상태다.
- 다음 작업에 영향을 줄 위험: 서비스 워커 캐시 전략은 배포 환경의 콘텐츠 헤더·HTTPS와 함께 검증해야 하며, W12 실제 공지 행 검증도 아직 남아 있다.
