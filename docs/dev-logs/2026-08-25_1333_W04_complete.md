## 1. 작업 개요

- 이번 작업 단위에서 만들기로 한 것: 장소 ID를 고유 키로 사용하는 IndexedDB 저장소와 조회·존재 확인·최초 저장 API를 만들고 Blob 영속화, 중복 방지, 저장 실패 처리를 자동 검증한다.
- 실제로 완료한 범위: `CollectionRecord` 계약, 버전 1 IndexedDB 스키마, 단건·전체·존재 조회, insert-only 최초 저장, 중복·동시 저장의 기존 기록 반환, 레코드 검증, IndexedDB 사용 불가·열기·읽기·쓰기·용량 초과 오류 모델을 구현했다. Vitest와 fake-indexeddb로 7개 통합 테스트를 추가했다.
- 범위에서 제외하거나 다음으로 넘긴 것: 사진 선택·형식 검증·압축과 성공 UI는 W05, 도감 UI와 삭제 가능성 안내는 W06 범위다. 진행 중인 W03의 실제 Kakao 지도 성공 검증은 올바른 JavaScript 키 확인 후 재개한다.

## 3. 구현 판단

- 선택한 구조 또는 접근: `chacha-campus` 데이터베이스의 `collection` object store에 `keyPath: "placeId"`를 사용했다. 저장은 `put()`이 아닌 `add()`만 사용하며, `ConstraintError`가 발생하면 같은 readwrite 트랜잭션에서 기존 레코드를 읽어 `existing`으로 반환한다. 트랜잭션의 `complete` 전에는 성공을 반환하지 않는다.
- 대안과 선택 이유: 저장 전 `get()` 후 `add()`하는 방식은 여러 탭이나 동시 요청 사이에 경쟁 조건이 생길 수 있어 사용하지 않았다. 고유 키와 insert-only `add()`가 실제 중복을 판정하도록 했다.
- Blob과 오류 처리: 사진은 구조화 복제를 지원하는 IndexedDB에 `Blob` 그대로 저장하고 MIME 타입과 유효한 획득일을 함께 검증한다. `QuotaExceededError`는 사용자 조치가 가능한 별도 `QUOTA_EXCEEDED` 코드로 변환하고, IndexedDB 미지원·열기·읽기·쓰기·손상 레코드를 각각 구분한다.
- 성공 판정 근거: MDN의 `IDBObjectStore.add()` 문서가 요청 `success` 이후에도 트랜잭션이 실패할 수 있어 `complete`를 확인해야 한다고 명시하므로 모든 읽기·쓰기는 트랜잭션 완료 시점에만 resolve한다.
- 서버 전송 경계: 모듈은 `src/lib/browser/` 아래에 있고 네트워크 API를 import하거나 호출하지 않는다. 테스트에서 전역 `fetch`가 한 번도 호출되지 않음을 검증했다.
- 작업 순서 판단: W03은 저장된 키가 Admin 키인 외부 자격증명 문제로 성공 경로 검증이 막혀 있다. `docs/DEVELOPMENT_PRIORITY.md`가 W02·W03·W04의 허용 가능한 순서 조정을 명시하고 W04는 W01에만 의존하므로, 독립 작업인 W04를 먼저 완료했다.

## 4. 문제 및 막힌 지점

- 증상 1: 샌드박스 안의 첫 `npm install --save-dev vitest fake-indexeddb`가 출력 없이 대기했다.
- 원인 1: 제한된 네트워크 환경에서 패키지 레지스트리 연결이 진행되지 않았다.
- 해결 전 영향: 자동 테스트 러너와 IndexedDB 모사가 준비되지 않았다.
- 증상 2: 첫 테스트 실행에서 Vitest가 `@/lib/browser/collection-db` 별칭을 찾지 못했다.
- 원인 2: Next.js의 TypeScript 경로 별칭이 Vitest 설정에 자동 전달되지 않았다.
- 증상 3: 첫 타입 검사에서 `unknown[]`의 요소를 `forEach`로 검증한 사실이 반환 타입 좁히기로 이어지지 않았다.
- 원인 3: TypeScript 제어 흐름 분석은 콜백 내부 assertion을 배열 전체의 타입으로 전파하지 않는다.
- 영향을 받은 범위: 위 문제는 테스트 환경과 정적 타입에 한정됐으며 제품 데이터는 생성되지 않았다.

## 5. 해결 방법

- 설치 문제: 승인된 네트워크 실행으로 동일한 npm 설치를 다시 수행해 개발 의존성을 내려받았다. 설치 결과 취약점은 0건이었다.
- 별칭 문제: `vitest.config.mts`에서 `@`를 `src` 절대 경로로 매핑했다. `.mts`를 사용해 Vite의 CommonJS/ESM 설정 경고도 제거했다.
- 타입 문제: 전체 조회 결과를 `map`으로 요소별 검증하고 검증된 값만 새 배열로 반환하도록 바꿨다.
- 같은 문제가 재발할 때 확인할 항목: IndexedDB 스키마 버전을 올릴 때 열린 탭의 `versionchange` 연결 종료가 유지되는지 확인하고, 저장 API에 `put()`이 유입되지 않았는지 테스트한다. 테스트 설정 파일 확장자를 `.mts`로 유지한다.

## 7. 미해결 사항 및 위험

- 남은 문제: W03은 올바른 Kakao JavaScript 키와 로컬 허용 도메인으로 실제 지도 타일·세 마커·링크를 검증해야 한다. W04 자체 완료 조건은 모두 충족했다.
- 임시 처리 또는 mock: 테스트에서만 fake-indexeddb를 사용하며 제품 번들 의존성이 아닌 devDependency다. 실제 Chrome 영속화는 W05 사진 인증 흐름을 연결할 때 브라우저에서 추가 검증한다.
- 외부 키·계정·콘텐츠 의존성: W04는 없음.
- 다음 작업에 영향을 줄 위험: 브라우저가 사이트 데이터를 삭제하거나 비공개 세션을 종료하면 IndexedDB 기록도 사라질 수 있다. 해당 사용자 안내는 W06에서 반드시 표시한다. 브라우저별 실제 할당량은 달라지므로 W05는 압축 실패와 저장 실패를 별도 성공 상태로 합치지 않는다.
