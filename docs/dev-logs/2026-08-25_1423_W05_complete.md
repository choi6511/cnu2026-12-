## 1. 작업 개요

- 이번 작업 단위에서 만들기로 한 것: 카메라 촬영 유도와 사진첩 입력, 이미지 검증·미리보기·재선택, 최대 1280px·품질 0.75 압축, 사진이 있을 때만 가능한 인증 완료, IndexedDB 최초 저장과 중복·오류 처리를 구현한다.
- 실제로 완료한 범위: 세 장소의 방문 인증 페이지에 공통 Client Component를 연결했다. JPG·PNG·WebP만 허용하고, `createImageBitmap`과 Canvas로 비율을 유지한 WebP 압축을 수행하며, Blob URL 미리보기와 정리, 다시 선택, 최초 획득 저장, 중복 인증 보존, 사용자용 오류 안내를 구현했다.
- 범위에서 제외하거나 다음으로 넘긴 것: 최초 획득 전체 화면 모달과 도감·장소 소개의 획득 상태 연결은 W06 범위다. 실제 Android 기기의 카메라 앱 호출은 발표 기기에서 W07/W15 실기기 검증으로 확인한다.

## 3. 구현 판단

- 선택한 구조 또는 접근: Server Component인 route page는 `placeId`, `placeName` 문자열만 Client Component에 전달한다. 파일·ImageBitmap·Canvas·Blob URL·IndexedDB는 모두 브라우저 전용 모듈과 Client Component에서만 사용한다.
- 압축 계약: 입력은 브라우저 대상과 예측 가능한 디코딩을 위해 JPEG, PNG, WebP로 제한했다. 긴 변이 1280px를 넘는 경우에만 축소하고, 결과는 `image/webp`, 품질 `0.75`로 저장한다. 작은 이미지는 확대하지 않는다.
- 중복 방지: 화면에서 저장 여부를 미리 판단하지 않고 W04의 insert-only `saveCollectionRecordOnce()` 결과를 사용한다. `existing`이면 새 Blob과 획득일을 버리고 최초 기록 유지 안내를 표시한다.
- 미리보기 자원 관리: 압축 Blob의 object URL만 미리보기에 쓰고, 사진 교체와 컴포넌트 unmount 시 이전 URL을 해제한다. 빠른 연속 선택은 요청 ID로 오래된 처리 결과가 현재 상태를 덮지 않게 한다.
- React/Next.js 검토: async 작업은 이벤트 핸들러 안에 두고 Client Component 자체를 async로 만들지 않았다. 상태에서 파생 가능한 버튼 disabled 값은 렌더 중 계산하고, Server→Client props는 원시 문자열만 사용하며, Blob 미리보기는 `next/image`의 `unoptimized` 경로로 렌더링했다.
- 개인정보 경계: 새 모듈과 컴포넌트에는 `fetch`, XHR, FormData, Supabase·Octoparse·비밀키 참조가 없다. 인증사진은 IndexedDB에서 끝난다.

## 4. 문제 및 막힌 지점

- 증상 1: 인앱 브라우저에서는 방문 인증 화면과 입력 요소를 확인할 수 있었지만 파일 입력에 로컬 파일을 주입하는 기능이 제공되지 않았다.
- 원인 1: 해당 브라우저 제어 API의 locator에는 파일 업로드 명령이 없었다.
- 해결 1: 파일 업로드 명령을 지원하는 `agent-browser` CLI를 `npx --yes`로 임시 실행해 별도 격리 세션에서 실제 파일 선택을 검증했다. 프로젝트 의존성이나 `package.json`에는 추가하지 않았다.
- 증상 2: 새 개발 서버 시작 시 포트 3000에서 같은 저장소의 기존 Next.js 개발 서버 PID 33152가 감지되어 새 프로세스가 3001을 시도한 뒤 종료됐다.
- 원인 2: 이전 검증에서 남은 Next.js 개발 프로세스가 같은 `.next` 디렉터리를 사용 중이었다.
- 해결 2: 기존 3000 서버가 현재 저장소를 제공한다는 Next.js 진단을 확인해 그 서버로 검증하고, 브라우저 검증 후 PID를 종료해 `PORT_3000_CLOSED`를 확인했다.
- 영향을 받은 범위: 두 문제 모두 검증 도구와 로컬 개발 서버 수명에 한정됐고 제품 저장 데이터나 소스 구조에는 영향을 주지 않았다.

## 5. 해결 방법

- 구현 중 검증 방법: 순수 크기 계산과 오류 분류는 Vitest로 검증하고, Canvas 압축은 `createImageBitmap`, Canvas context, `toBlob`을 모사해 출력 형식·품질·크기를 확인했다. 실제 Chrome에서는 저장소의 WebP 파일을 두 입력에 업로드해 미리보기와 IndexedDB 저장을 확인했다.
- 최초 저장 검증: 중앙도서관 사진첩 입력에 `library.webp`를 선택해 `1200 × 800px · 압축 완료`, 활성화된 인증 버튼, `처음 획득했습니다` 상태를 확인했다.
- 중복 검증: 새로고침 후 같은 중앙도서관에 `language-center.webp`를 제출해 `처음 저장한 사진과 획득일을 그대로 유지했습니다` 상태를 확인했다. W04 자동 테스트가 실제 최초 Blob·날짜 불변도 바이트 단위로 검증한다.
- 실패 검증: `package.json`을 사진첩 입력에 넣어 JPG·PNG·WebP 안내, 미리보기 없음, 인증 버튼 비활성화를 확인했다. 디코딩 실패는 자동 테스트로 검증했다.
- 같은 문제가 재발할 때 확인할 항목: 파일 input의 `accept`와 카메라 input의 `capture="environment"`, object URL 해제, Canvas 출력 MIME, 저장 결과가 `created | existing`인지, 오류 후 인증 버튼이 비활성인지 확인한다.

## 7. 미해결 사항 및 위험

- 남은 문제: W05 코드 범위의 미해결 기능은 없다. 실제 Android Chrome에서 후면 카메라 앱이 열리고 촬영 결과가 돌아오는지는 발표 기기에서 확인해야 한다.
- 임시 처리 또는 mock: 자동 테스트는 Canvas와 IndexedDB를 모사하지만, 완료 판정에는 실제 Chromium 파일 입력·Canvas 압축·IndexedDB 저장 결과도 사용했다. 테스트 사진은 프로젝트의 임시 장소 WebP 자산이다.
- 외부 키·계정·콘텐츠 의존성: 없음. 방문 인증은 온라인 연결 없이 동작하도록 네트워크 호출을 사용하지 않는다.
- 다음 작업에 영향을 줄 위험: `createImageBitmap`을 지원하지 않는 오래된 브라우저에서는 읽기 실패 안내가 표시된다. 주 테스트 환경인 최신 Android·데스크톱 Chrome에서는 지원된다. W07에서 실제 대용량 휴대폰 사진과 EXIF 회전 방향을 확인한다.
- 데이터 위험: 브라우저 사이트 데이터 삭제나 앱 제거 시 사진·획득 기록이 사라진다. 사용자 안내와 도감 표시 책임은 W06에 남아 있다.
