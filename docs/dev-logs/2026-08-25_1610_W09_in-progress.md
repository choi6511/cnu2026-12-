## 1. 작업 개요

- 이번 작업 단위에서 만들기로 한 것: `docs/dev-logs/2026-08-25_1028_W09_in-progress.md`에서 남겨둔 W09 잔여 범위 중, Vercel·Supabase 플러그인 없이 독립적으로 진행 가능한 코드 범위(브라우저/서버 Supabase 클라이언트 분리, KST 최근 7일 경계 유틸리티, crawl_runs 공개 정책 축소 마이그레이션 파일)를 구현한다.
- 실제로 완료한 범위: `src/lib/supabase/public.ts`, `src/lib/supabase/server.ts`, `src/lib/notices/types.ts`, `src/lib/notices/date-kst.ts`와 경계 테스트, 후속 마이그레이션 SQL 파일 작성. 타입 검사·린트·테스트·빌드 통과.
- 범위에서 제외하거나 다음으로 넘긴 것: 후속 마이그레이션의 원격 적용, anon 읽기/쓰기 권한의 실제 재검증, Security Advisor 재확인 — 모두 Supabase 플러그인이 필요하며 이번 세션에서 인증되지 않았다.

## 3. 구현 판단

- 선택한 구조 또는 접근: `docs/SYSTEM_ARCHITECTURE.md` 9장이 미리 정의한 `lib/supabase/public.ts`, `lib/supabase/server.ts`, `lib/notices/date-kst.ts` 경로를 그대로 따랐다. 새 구조를 고안하지 않고 문서의 목표 구조를 코드로 옮겼다.
- 대안과 선택 이유: 브라우저 클라이언트는 예외를 던지는 대신 `null`을 반환하도록 했다. 카카오맵 컴포넌트가 이미 `missing-key` 상태를 UI로 처리하는 관례(`src/components/map/campus-map.tsx`)와 맞추어, W12에서 공지 UI가 같은 방식으로 "설정 필요" 상태를 보여줄 수 있게 했다.
- 마이그레이션 적용 여부 판단: 새 마이그레이션 파일은 작성했지만 원격에는 적용하지 않았다. `AGENTS.md`는 Supabase 변경 후 실제 프로젝트 상태를 Supabase 플러그인으로 재검증하도록 요구하는데, 이번 세션은 그 플러그인이 인증되지 않아 적용과 검증을 동시에 할 수 없다. 검증 없이 원격에 적용만 하면 "가짜 성공"이 될 위험이 있어, 플러그인이 연결될 때까지 파일 상태로만 남겼다.
- 작업 순서 판단: `docs/DEVELOPMENT_PRIORITY.md` 순서상 W09는 W08 완료 후 진행해야 한다. 그러나 이번 세션에서 W08은 Vercel 플러그인 인증 부재로 앱 코드와 무관한 외부 증거 게이트에서만 막혀 있고(`docs/dev-logs/2026-08-25_1545_W08_blocked.md`), W09의 이번 범위는 Supabase 원격 상태나 W08의 배포 여부에 의존하지 않는 순수 코드다. `AGENTS.md` 6장의 우선순위 변경 규칙(막힌 이유 기록, 독립 개발 가능한 범위만 수행, P0 흐름 약화 금지)에 따라 이 범위로 한정해 작업 단위를 전환했다. P0 코드나 배포 상태는 건드리지 않았다.

## 4. 문제 및 막힌 지점

- 증상: 새 마이그레이션을 원격에 적용하거나 anon/service_role 권한을 재검증할 수 없다.
- 재현 방법: 이번 세션에서 Supabase 플러그인 도구를 호출한다.
- 원인: `docs/dev-logs/2026-08-25_1545_W08_blocked.md`에서 확인한 것과 동일하게, `plugin:supabase:supabase`가 이번 세션에서 인증되지 않았고 비대화형 세션이라 인증을 대신할 수 없다.
- 영향을 받은 범위: 후속 마이그레이션의 원격 적용, `docs/ERD.md` 7장의 6개 검증 항목(anon 공지 SELECT 성공, anon 쓰기 실패, anon 성공 실행 SELECT 성공, anon 실패 실행 SELECT 0건, 서버 역할 쓰기 성공, Security Advisor 오류 0건).

구현 자체를 막은 문제는 없었음. 클라이언트 분리와 날짜 유틸리티는 외부 연결 없이 완성하고 검증했다.

## 5. 해결 방법

- 시도한 방법: Supabase 플러그인 도구 상태를 재확인하고, 플러그인 없이 가능한 코드·자동 테스트 범위로 작업을 한정했다.
- 최종 해결책: 없음(원격 검증 자체는). 코드 범위는 완료했고, 원격 적용은 플러그인 인증 후로 미뤘다.
- 같은 문제가 재발할 때 확인할 항목: Supabase 플러그인이 인증된 뒤 가장 먼저 `supabase/migrations/20260825154500_restrict_crawl_runs_public_read_to_success.sql`을 적용하고, `docs/ERD.md` 7장의 6개 항목을 그 플러그인으로 순서대로 확인한다.

## 7. 미해결 사항 및 위험

- 남은 문제: W09 완료 조건인 "공개 키로 읽기만 가능하고 쓰기는 거부된다"와 "Security Advisor 재확인"은 Supabase 플러그인 없이 공식적으로 닫을 수 없다.
- 임시 처리 또는 mock: 없음. 새 Supabase 클라이언트 모듈은 아직 어떤 화면에서도 import하지 않아(W12 범위), 이번 세션의 빌드·번들 결과에 영향을 주지 않는다.
- 외부 키·계정·콘텐츠 의존성: Supabase 플러그인 인증, `.env.local`의 `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` 실제 값 설정(로컬 개발 시), Vercel production 환경변수 추가(W14 통합 시).
- 다음 작업에 영향을 줄 위험: W08의 Vercel 플러그인 증거와 W09의 Supabase 원격 검증이 모두 같은 종류의 세션 인증 문제로 막혀 있다. 두 플러그인이 함께 인증되기 전까지는 코드 범위 밖의 진전이 없다.
