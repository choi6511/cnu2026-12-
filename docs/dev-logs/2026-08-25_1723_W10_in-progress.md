## 1. 작업 개요

- 이번 작업 단위에서 만들기로 한 것: Apify가 수집한 공지 결과를 안전한 수동 SQL로 반영하고 실제 DB 상태를 확인한다.
- 실제로 완료한 범위: 운영자가 SQL Editor에서 제공 스크립트를 실행했고, 연결된 Supabase 프로젝트에서 `notices` 30행과 `crawl_runs` 3행을 확인했다.
- 범위에서 제외하거나 다음으로 넘긴 것: W10의 JSON fixture 및 자동 검증 테스트는 아직 구현하지 않았다.

## 3. 구현 판단

- 선택한 구조 또는 접근: `notices`는 `(source_id, original_url)` 충돌 시 최신 제목·게시일·수집 시각으로 upsert하고, `crawl_runs`는 동일한 시작·종료 시각의 실행 로그가 이미 있으면 삽입하지 않게 했다.
- 대안과 선택 이유: RLS, 공개 읽기 권한, 비밀 키를 변경하지 않고 기존 테이블에 데이터만 반영했다.
- PRD 또는 기존 구현과의 관계: 사용자 사진·회원 데이터는 넣지 않았고, 공지 메타데이터와 운영 로그만 저장했다.

## 4. 문제 및 막힌 지점

- 증상: Codex의 Supabase SQL 호출은 워크스페이스 지출 한도 때문에 계속 사용할 수 없다.
- 재현 방법: Codex Supabase `execute_sql` 호출.
- 원인: 워크스페이스 승인 한도이며 DB·RLS·수집 결과의 결함이 아니다.
- 영향을 받은 범위: Codex에서 직접 SQL 표본 조회는 불가하나, 사용자의 SQL Editor 실행과 연결된 테이블·Advisor 읽기 검증으로 대체했다.

## 5. 해결 방법

- 시도한 방법: Apify 실제 결과로 SQL을 생성하고 사용자가 Supabase SQL Editor에서 실행했다.
- 최종 해결책: SQL Editor의 트랜잭션 upsert로 30개 공지와 세 성공 로그를 반영했다.
- 같은 문제가 재발할 때 확인할 항목: SQL Editor 실행 계정의 프로젝트 권한, `notices`/`crawl_runs` 행 수, Security Advisor 결과.

- 외부 키·계정·콘텐츠 의존성: 이후 갱신은 Apify OAuth와 Supabase SQL Editor 권한 또는 Codex 지출 한도 해소가 필요하다.
