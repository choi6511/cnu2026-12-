# 개발 우선순위와 작업 단위

이 문서는 `PRD.md`의 MVP, 핵심 시연 장면, 기능별 완료 조건, 필수 테스트 시나리오를 실제 구현 의존성에 맞게 재배열한 실행 계획이다. 위에서 아래 순서로 진행하며, 각 작업 단위는 구현과 검증을 모두 마친 뒤 다음 세션으로 넘긴다.

## 우선순위 원칙

1. **P0 핵심 시연 흐름 우선**: 지도에서 장소를 찾아 사진을 제출하고 캐릭터가 도감에 남는 흐름을 가장 먼저 완성한다.
2. **실행 가능한 골격 우선**: 화면 기능에 앞서 타입 검사·빌드가 가능한 최소 프로젝트를 만든다.
3. **수직 완성 우선**: UI만 만든 뒤 데이터 기능을 몰아서 붙이지 않고, 사용자에게 보이는 흐름 단위로 저장과 오류 처리까지 연결한다.
4. **P1 제품 약속 후속**: 공지 수동 갱신, PWA, 오프라인은 P0 시연 흐름이 검증된 뒤 구현한다.
5. **P2는 선택 사항**: P0과 P1 완료 및 회귀 검증 후에만 진행한다.

## 작업 단위 목록

### W00 — 프로젝트 골격과 안전한 설정 (P0 기반)

범위:

- Next.js App Router, TypeScript 프로젝트 생성
- 기본 실행·타입 검사·린트·빌드 명령 확립
- `.gitignore`, 값이 비어 있는 `.env.example` 작성
- 필요한 환경변수 접근 구조와 서버/클라이언트 경계 설정

완료 조건:

- 개발 서버가 실행되고 기본 페이지가 열린다.
- 타입 검사, 린트, 프로덕션 빌드가 통과한다.
- 비밀 환경변수가 브라우저 코드나 추적 파일에 포함되지 않는다.

필수 검증: PRD 테스트 12의 저장소 측 검증.

### W01 — 정적 장소 도메인과 앱 셸 (P0 기반)

선행 조건: W00

범위:

- 세 장소만 포함한 타입 안전 정적 데이터
- `/`, `/places/[slug]`, `/places/[slug]/verify`, `/places/[slug]/notices`, `/collection` 라우팅 골격
- 모바일 우선 레이아웃과 `지도`·`캐릭터 도감` 하단 내비게이션
- 존재하지 않는 slug 처리
- 규격이 고정된 임시 장소·캐릭터 자산 경로

완료 조건:

- 모든 경로가 올바른 장소 데이터를 사용한다.
- 세 장소 외 데이터가 노출되지 않는다.
- 모바일 뷰에서 핵심 콘텐츠가 하단 내비게이션에 가리지 않는다.

필수 검증: 세 slug 라우팅, 잘못된 slug, 하단 메뉴 이동.

### W02 — 장소 소개 화면 (P0)

선행 조건: W01

범위:

- 대표 이미지, 장소명, 소개, 위치 설명
- 공지 및 방문 인증 버튼
- 정적 콘텐츠의 오프라인 사용을 고려한 서버/정적 렌더 구조
- 획득 상태를 나중에 연결할 수 있는 명확한 UI 자리

완료 조건:

- 세 장소의 콘텐츠와 링크가 서로 정확히 일치한다.
- 소개 콘텐츠가 외부 API 없이 렌더링된다.

필수 검증: PRD의 장소 소개 완료 조건.

### W03 — 카카오맵과 세 장소 진입 (P0)

선행 조건: W01, 장소 좌표 확인

범위:

- 클라이언트에서만 카카오맵 SDK 초기화
- 충남대 캠퍼스 중심 지도와 세 고정 마커
- 마커 라벨/정보창과 올바른 장소 소개 이동
- SDK 로딩 실패 및 오프라인 안내

완료 조건:

- 온라인 Chrome에서 세 마커와 올바른 링크가 동작한다.
- GPS 권한을 요청하지 않는다.
- 오프라인 또는 SDK 오류 시 빈 화면이 아닌 안내가 표시된다.

필수 검증: PRD 테스트 2, 9 및 지도 완료 조건.

### W04 — IndexedDB 도감 저장 기반 (P0)

선행 조건: W01

범위:

- `CollectionRecord` 타입과 `placeId` 고유 키 저장소
- 조회, 최초 저장, 존재 확인 API
- Blob 저장 및 저장 공간/IndexedDB 오류 처리
- 서버 전송이 없음을 보장

완료 조건:

- 장소별 레코드를 한 번만 저장하고 새로고침 후 읽을 수 있다.
- 중복 저장이 기존 사진이나 획득일을 교체하지 않는다.
- 저장 실패를 성공으로 표시하지 않는다.

필수 검증: IndexedDB CRUD 자동 테스트 또는 브라우저 통합 테스트, 중복·실패 경로.

### W05 — 사진 선택·압축·방문 인증 (P0)

선행 조건: W02, W04

범위:

- 카메라 촬영 유도 입력과 사진첩 입력
- 이미지 형식 검증, 미리보기, 다시 선택
- 최대 1280px와 품질 약 0.75의 클라이언트 압축
- 사진이 있을 때만 활성화되는 인증 완료
- 최초 획득 저장, 중복 인증 방지, 처리 오류 표시

완료 조건:

- 두 입력 경로가 모두 존재하고 이미지가 아닌 파일을 거부한다.
- 압축 결과와 획득 정보가 IndexedDB에 저장된다.
- 같은 장소의 두 번째 인증은 기존 기록과 사진을 바꾸지 않는다.

필수 검증: PRD 테스트 4, 5, 6, 7 및 방문 인증 완료 조건.

### W06 — 획득 연출과 캐릭터 도감 연결 (P0)

선행 조건: W05

범위:

- 최초 획득 때만 표시되는 획득 모달
- 세 고정 슬롯, 잠금 실루엣, 획득 이미지·날짜
- 진행 상태 `3개 중 N개 획득`
- 획득 카드의 인증사진 표시와 Blob URL 정리
- 장소 소개의 획득 완료 상태
- 로컬 데이터 삭제 가능성 안내

완료 조건:

- 최초 실행, 일부 획득, 전체 획득 상태가 정확하다.
- 새로고침 후에도 캐릭터와 인증사진이 보인다.
- 같은 장소 재인증으로 개수가 늘거나 모달이 다시 나오지 않는다.

필수 검증: PRD 테스트 1, 5, 6, 7 및 도감 완료 조건.

### W07 — P0 핵심 흐름 회귀 검증 (P0 게이트)

선행 조건: W00–W06

범위:

- 지도 → 소개 → 인증 → 최초 획득 → 도감 전체 흐름
- 세 장소 데이터 정합성
- 새로고침과 중복 인증 회귀
- 모바일 세로 화면에서 2분 내 시연 리허설

완료 조건:

- 핵심 흐름을 설명 제외 2분 내 완료한다.
- 관련 자동 검사와 프로덕션 빌드가 모두 통과한다.
- 발견한 회귀 결함을 모두 수정하고 재검증한다.

필수 검증: PRD 테스트 1, 2, 4, 5, 6, 7.

### W08 — P0 핵심 흐름 Vercel 배포 (P0 배포 게이트)

선행 조건: W07, GitHub 및 Vercel 프로젝트 설정

범위:

- GitHub–Vercel 연결과 프로덕션 배포
- 카카오맵 키와 허용 도메인 설정
- P0에 필요한 공개 환경변수 설정
- 배포 환경의 빌드 및 모바일 핵심 흐름 검증

완료 조건:

- HTTPS 프로덕션 URL에서 지도 → 소개 → 인증 → 획득 → 도감 흐름이 동작한다.
- 카카오맵이 프로덕션 허용 도메인에서 정상 표시된다.
- 저장소와 브라우저 번들에 비밀값이 없다.

필수 검증: 프로덕션 모바일 Chrome에서 P0 핵심 흐름과 새로고침·중복 인증 테스트.

### W09 — Supabase 공지 데이터 기반 (P1)

선행 조건: W08, Supabase 프로젝트 설정

범위:

- `notices`, `crawl_runs` 스키마·제약·인덱스
- RLS, 공개 SELECT 정책, 서버 전용 쓰기 권한
- 브라우저 읽기와 서버 쓰기 클라이언트 분리
- KST 최근 7개 달력 날짜 계산 유틸리티

완료 조건:

- 공개 키로 읽기만 가능하고 쓰기는 거부된다.
- secret key가 클라이언트 번들에 포함되지 않는다.
- 날짜 경계 테스트가 통과한다.

필수 검증: PRD 테스트 12, 최근 7일 경계 테스트.

### W10 — 출처별 Apify Actor 실행 (P1)

선행 조건: W09, 실제 홈페이지 HTML 구조 확인

범위:

- 세 출처별 독립 Apify Actor 실행
- 제목, 게시일, 절대 원문 URL, 수집 시각 정규화
- 추측하지 않고 실제 Apify 결과에 근거한 필드 매핑과 JSON fixture 테스트
- Apify 실행·결과 검증·DB 오류 구분

완료 조건:

- 세 작업 결과를 동일한 `NoticeInput[]`으로 검증할 수 있다.
- 잘못된 날짜는 제외되고 실패 원인이 기록된다.
- Apify 결과 fixture에 대한 검증 테스트가 통과한다.

필수 검증: 실제 수동 수집과 저장값 표본 확인.

### W11 — 운영자 수동 갱신과 Supabase 반영 (P1)

선행 조건: W10

범위:

- 운영자가 Codex에 `공지 갱신해줘`라고 요청하는 단일 수동 절차
- Apify Actor 검색·실행·완료 대기·dataset 결과 내보내기
- 출처별 독립 실행과 성공 출처만 upsert
- 실패 출처 데이터 보존 및 출처별 실행 로그
- Supabase 플러그인으로 저장 결과와 표본 재검증

완료 조건:

- 운영자의 명시적 요청 없이는 작업이 실행되지 않는다.
- 한 출처 실패가 다른 출처의 저장을 막지 않는다.
- 실패한 출처의 기존 공지와 마지막 성공 기록이 유지된다.
- 수동 실행 뒤 출처별 성공·실패·반영 개수가 운영자에게 보고된다.

필수 검증: PRD 테스트 10, 11.

### W12 — 장소별 최근 공지 UI (P1)

선행 조건: W09, 가능하면 W11

범위:

- 장소별 최근 7일 공지 최신순 조회
- 제목, 작성일, 새 탭 원문 링크
- 마지막 성공 갱신 시각
- 로딩, 빈 결과, 오류, 오프라인 상태

완료 조건:

- 장소가 다른 공지가 섞이지 않는다.
- 오늘 포함 7개 KST 달력 날짜만 표시한다.
- 원문 링크와 마지막 성공 갱신 시각이 정확하다.

필수 검증: PRD 테스트 3 및 공지 완료 조건.

### W13 — PWA 설치와 제한적 오프라인 (P1)

선행 조건: W08, W12

범위:

- 유효한 manifest, 192/512 아이콘, standalone 설정
- HTTPS에서 등록되는 Service Worker
- 앱 셸, 정적 장소 소개, 도감과 저장 사진의 오프라인 동작
- 지도와 공지의 오프라인 안내

완료 조건:

- Chrome에서 설치 가능 조건을 충족한다.
- 오프라인에서 소개와 도감이 열리고 지도·공지는 안내를 표시한다.
- 서비스 워커 갱신이 새 배포를 영구적으로 가리지 않는다.

필수 검증: PRD 테스트 8, 9와 PWA 완료 조건, Lighthouse 또는 실제 Chrome 설치 확인.

### W14 — 프로덕션 운영 통합 (P1 배포 게이트)

선행 조건: W08, W11, W13

범위:

- P1 변경 사항의 프로덕션 재배포
- Supabase 공개/비공개 환경변수 분리
- Apify·Supabase 수동 갱신 절차 확인
- HTTPS 환경의 공지 조회와 PWA 설치 검증

완료 조건:

- 프로덕션 URL에서 기존 P0 흐름과 공지 조회가 모두 동작한다.
- 발표 직전 수동 갱신과 저장 표본 확인이 성공한다.
- secret이 저장소와 브라우저 번들에 없다.

필수 검증: 프로덕션 모바일 Chrome에서 핵심 흐름과 설치 테스트.

### W15 — 최종 회귀와 발표 준비 (릴리스 게이트)

선행 조건: W00–W14

범위:

- PRD 필수 테스트 시나리오 1–12 전체 수행
- 세 장소의 지도 좌표, 콘텐츠, 캐릭터, 공지 링크 확인
- 온라인·오프라인·크롤러 부분 실패 시연 준비
- 2분 핵심 흐름 최종 리허설

완료 조건:

- 필수 테스트 12개가 모두 통과하거나, 발표를 막지 않는 잔여 위험이 명시적으로 기록된다.
- 배포 버전과 테스트한 버전이 동일하다.
- 시연에 필요한 기기와 데이터가 준비된다.

### W16 — 선택 개선 (P2)

선행 조건: W15

범위:

- 획득 모달 추가 애니메이션
- 커스텀 지도 마커
- 세밀한 반응형 조정
- 접근성 문구와 키보드 탐색 강화

완료 조건: 선택한 개선이 P0/P1 회귀를 만들지 않고 관련 검증을 통과한다.

## 진행 순서 요약

```text
W00 → W01 → W02 → W03 → W04 → W05 → W06 → W07 → W08(P0 배포)
                                                       ↓
W09 → W10 → W11 → W12 → W13 → W14 → W15 → W16(선택)
```

W02와 W03, W04는 코드 의존성이 허용하는 범위에서 순서를 조정할 수 있지만, 세션당 한 작업 단위 원칙은 유지한다. W05를 시작하기 전에는 W02와 W04가 모두 완료되어야 한다.

### 현재 예외 순서

2026-08-25에 W10의 Octoparse 제약은 사용자 요청에 따라 Apify MCP/Actor로 교체됐다. 같은 날 Apify MCP 연결, 세 출처 Actor 실행, 실제 출력 fixture 검증과 30개 공지·3개 실행 로그의 Supabase 반영을 확인했다. W11은 이 결과를 바탕으로 다음 운영자 요청에서도 세 출처 독립 실행·성공 출처만 upsert·실패 데이터 보존을 반복 검증한다. W12는 W09만 선행하면 독립적으로 가능한 예외 작업으로 먼저 구현됐으며, 이제 실제 저장 데이터로 화면을 재검증할 수 있다.

W12의 실제 공지 행·원문 링크 확인은 W11 결과를 기다려야 하지만, W13의 manifest·Service Worker·정적 경로 오프라인 기반은 W12의 현재 UI 구현만으로 독립 검증할 수 있다. 따라서 W10/W11 차단 기간에는 W13을 구현·로컬 검증하고, 프로덕션 설치·오프라인 최종 증거는 W14에서 W12 재검증과 함께 수집한다.
